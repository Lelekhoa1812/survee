# KQA design system and agent guidance

Version: `kqa-design/23` · reviewed 19 November 2026

This is the product-specific design policy for KQA's host console, respondent questionnaires, and analytics. Agents can retrieve the same principles through the read-only `get_design_guidance` MCP tool; its review checklist is scoped to the requested surface, and `all` returns the full checklist. KQA does not include an LLM: connected agents decide how to apply these instructions and should return their rationale and review evidence.

The tool also returns a structured `designPlan` contract for moving from a user brief through question-content review, design, implementation, task-based usability, and critique. Its question-content rubric and cognitive pretest method, output fields, guardrails, WCAG-EM method, and task-usability method help agents record separate evidence. The content protocol supports comprehension, recall, judgment, and response-selection probes; a moderated session may combine those probes with usability tasks, but findings remain distinct. For machine-readable agent critique, follow `output.questionContentReview.findingContract` verbatim: each finding has a stable question location, recognized category, severity, confidence, evidence, rationale, and recommendation; use `findings`, `no_findings`, or `needs_context` as appropriate. The benchmark scorer uses a separate results format and only measures location/category matching plus required fields; it does not determine whether evidence or recommendations are substantively correct. Its public development cases and limitations are documented in [`evals/QUESTIONNAIRE_AUTHORING_BENCHMARK.md`](evals/QUESTIONNAIRE_AUTHORING_BENCHMARK.md); scores are not validation or respondent evidence. `output.reviewEvidenceMatrix` requires each selected QA sample to record its surface/route, state/theme, viewport/input method, criterion, method/tool, observed result, evidence reference, and limitation or untested reason. Record untested checks explicitly and keep respondent personal data out of references. Visual-taste guidance is heuristic: preserve the user's explicit direction and product context, and do not present a subjective preference as a standard. WCAG 2.2 AA remains the accessibility target.

When a user supplies a theme, the read-only MCP tool `extract_design_profile` can parse CSS custom properties, legacy token JSON, or a bounded subset of the [Design Tokens Format Module 2025.10](https://www.w3.org/community/reports/design-tokens/CG-FINAL-format-20251028/) into scoped semantic-role candidates, provenance, ambiguity, and limited solid-color contrast calculations. The Format Module is a W3C Design Tokens Community Group specification, not a W3C Standard. For DTCG JSON, the importer supports nested groups and group `$root` tokens, `$value`, inherited `$type`, selected color/dimension/font-family value forms, curly-brace aliases, inline JSON Pointer references, and top-level `light`/`dark` groups. It follows the [DTCG Color Module 2025.10](https://www.designtokens.org/TR/2025.10/color/): a hex fallback does not cancel alpha, so colors with alpha other than 1 stay in manual review and are excluded from opaque CSS overlays and inferred contrast checks. Curly aliases to a group-root token use the explicit `group.$root` path; a group name alone does not identify its root token. It reports or leaves unresolved `$extends` group inheritance, resolver-file mode permutations, external references, unsupported value forms, and ambiguous aliases; it does not fetch additional files. It returns a proposal overlay for review and never fetches, executes, stores, or applies the input. Its contrast calculations do not replace rendered accessibility checks.

For host surfaces, `visualProfile.host` exposes the default KQA visual direction, semantic token names, and core light/dark token values from `src/app/globals.css`. The default is a heuristic when the user has not supplied a different brand or theme; it is not a template to force onto every interview. Filled danger surfaces use the paired `--danger` and `--danger-ink` tokens; verify contrast for all actual foreground/background pairs. The stylesheet does not currently define a shared spacing scale. Questionnaire guidance is separate because its HTML runs in a sandboxed iframe and does not inherit host CSS variables; `visualProfile.questionnaire` exposes tokens and layout conventions from [`template/starter.kqa.html`](template/starter.kqa.html), while [`FORMAT.md`](FORMAT.md) documents the supported controls and runtime. Analytics guidance emphasizes legible labels, provenance, denominators, non-color chart alternatives, and singleton disclosure signals; KQA does not suppress small groups by default.

## Product constraints

- Questionnaires are self-contained HTML files rendered in a sandboxed frame. Follow [`FORMAT.md`](FORMAT.md) for allowed controls, runtime behavior, and network restrictions.
- Use declarative `when` rules for supported choice comparisons or to check whether an earlier answer is present. Mark each whole question block so KQA can hide and disable it; explain that an inactive answer is retained and excluded from current-rule progress and analysis. Do not imply current eligibility proves the question was displayed at an earlier time.
- There is no in-app question builder and no scoring. Keep authoring as questionnaire HTML plus the checker; keep answer analysis descriptive.
- Preserve question and option ids when revising a live interview. Run the checker and inspect compatibility findings before creating a new immutable survey version.
- Keep private respondent links and individual answers out of unrelated views, logs, and aggregate analytics.

## Design principles

1. **Make the task obvious.** Lead with the user's task, next action, and current state. Use concrete labels and plain language. Explain consequences before destructive actions.
2. **Make live status freshness clear.** Participant progress and activity are snapshots, not a live stream. Provide a clear manual refresh where live status matters, identify what it refreshes, and do not imply automatic or real-time updates.
3. **Fit the intended theme.** Treat the supplied brand, audience, and tone as design constraints. Use a compact set of semantic color, typography, spacing, and shape tokens. Keep contrast and focus legible across themes; never use color alone to communicate meaning.
4. **Make visual choices specific to the brief.** Choose palette, type, layout, and motion for this product, audience, and task. Treat familiar product patterns as options rather than defaults; keep a distinctive motif only when it supports the brief and remove decoration that adds no meaning. The user's direction takes precedence over this heuristic.
5. **Keep respondents oriented and in control.** Use clear sections, concise progress, visible save state, and explicit submission consequences. For long forms, use section-aware navigation or opt-in guided steps; choose the journey that fits the task, not the interface novelty. Guided steps need Back, preserved answers, validation when Continue is chosen, a clear escape to all questions, and a standard final review. Follow conditional eligibility without discarding answers, and announce route changes without stealing focus. Distinguish saved answers from edits waiting to sync. Explain which routed answers are omitted and retained. Mark required questions and explain material changes to stored answers.
6. **Ask clear, neutral questions.** Ask one thing at a time in familiar, audience-appropriate language. Avoid leading assumptions, vague terms, double negatives, and items that combine separate ideas. State a reference period for time-bound behavior.
7. **Make response options fit the question.** Make closed options distinct and broad enough to cover reasonable answers. Use balanced scale labels with a consistent direction. Add a neutral point or options like "not applicable", "not sure", "prefer not to answer", and "other" only when they fit the construct. Keep options stable when comparing versions.
8. **Pretest with intended respondents.** For new or high-impact items, use the question-content rubric and cognitive pretest protocol returned by `get_design_guidance` with people like the intended respondents. Probe comprehension, recall, judgment, and response selection. Record participant fit, item and context tested, observations, severity, revisions, and remaining uncertainty. A cognitive probe and end-to-end usability task may share a moderated session, but retain separate findings.
9. **Test complete tasks with representative users.** For new or materially changed flows, observe intended users completing realistic end-to-end tasks. Record task completion, hesitation, errors, recovery, and misunderstandings. Report who was represented, which tasks and success criteria were used, observations, and limitations. If sessions did not happen, say usability is untested. Keep this separate from question-item pretesting and WCAG evaluation.
10. **Make every interaction operable.** Prefer native semantic controls, programmatic labels, and built-in keyboard behavior. Custom radio groups must follow the WAI-ARIA APG pattern. Keep focused controls fully visible around fixed or sticky UI (WCAG 2.4.11); provide a non-drag alternative for dragging interactions (WCAG 2.5.7). Errors should identify the affected field and explain a correction, and status/errors must reach assistive technology. Meet WCAG 2.2 AA, including the 24 × 24 CSS-pixel minimum target size or a documented exception such as sufficient spacing. Verify keyboard and assistive-technology behavior.
11. **Design for narrow screens and long content.** Reflow at 320 CSS px where WCAG requires it. KQA questionnaires must work from 360 px and should be checked at 390 px. Test long labels, validation, tables, zoom, empty states, and errors.
12. **Use motion to clarify change.** Animate to communicate state or continuity. Keep motion brief, and ensure `prefers-reduced-motion` leaves the interface fully understandable.
13. **Show how every number was made.** State survey version, participant status scope, time window when used, status-cohort denominator, eligible and inactive counts, eligible no-answer count, and valid n. Eligibility is inferred from current routing rules and saved answers; it is not a historical record that a conditional question was displayed. For ordinal scales show distributions rather than means. For multi-select, make clear that percentages use valid eligible respondents and can sum above 100%. Separate observed facts from interpretation; do not imply causality, statistical significance, or a score.
14. **Minimize answer exposure.** Aggregate by default. Show person-level answers only for an explicit review task. Do not expose private links or raw answers in analytics, logs, or unrelated exports.

## Review checklist

- Is the task and its outcome clear without color or animation?
- Can a keyboard-only user operate the full flow and see where focus is?
- Are pointer targets at least 24 × 24 CSS px, or covered by a WCAG 2.2 SC 2.5.8 exception such as sufficient spacing?
- Do controls have labels, errors explain recovery, and save/submission status reach assistive technology?
- Is keyboard focus unobscured around fixed/sticky UI, is there a non-drag alternative for dragging, and do errors identify the affected field and explain a correction?
- Are native radio controls used where possible; if custom radio groups are necessary, do they follow the WAI-ARIA APG arrow-key and Tab pattern?
- Have WCAG 2.2 AA contrast and reflow been checked at 320 CSS px, plus KQA's 360/390 px questionnaire widths?
- Have empty, loading, saving, success, error, submitted, long-content, dark-theme, and reduced-motion states been reviewed?
- Before submission locks responses, can respondents review readable answer values and notes, understand any unresolved items, and return to edit the relevant question? Is the treatment of currently inactive retained answers explained?
- For long questionnaires, can a respondent navigate by section and jump to an eligible question using keyboard and a narrow viewport? If guided steps are enabled, can they go back, find and fix step errors, switch to all questions, and review answers? Do counts follow saved answers and routing without unexpected focus movement?
- For live interview status, can a manager refresh the participant progress snapshot, and is it clear that updates are manual rather than real time?
- Does each question ask one clear thing, use neutral wording, and state an appropriate reference period?
- Are closed options distinct and sufficient for reasonable answers, and are scale labels and option ordering intentional?
- Were new or high-impact questions pretested with people like the intended respondents where feasible?
- Do cognitive pretest notes show who was represented, which items/context were tested, the probe dimension, findings, revisions, and unresolved issues? Is usability evidence kept distinct?
- For new or materially changed flows, did representative users attempt realistic end-to-end tasks? Record task success, hesitation, errors, recovery, misunderstandings, participant context, and limitations; mark usability untested if no sessions were run. This is separate from item pretesting and WCAG evaluation.
- Are ids stable, required questions visible, and data-impacting survey changes explained?
- Are conditional reveals simple, with multipart follow-ups presented as a separate step where supported or redesigned as a simpler non-conditional flow? Explain input-driven changes of context before they happen. Test show/hide, focus, restored answers, and locked states with keyboard and representative screen reader/browser combinations; record combinations not tested. A reveal or ARIA attribute alone does not establish accessibility.
- Is the handling of earlier answers when a condition changes decided and disclosed, including how respondents can remove an answer? Consider the collection purpose and sensitivity. Inactive answers are retained; eligibility is inferred from current rules and answers, not stored as a historical display event. A required routed question is required only while eligible. See the [agent playbook](AGENT_PLAYBOOK.md#mapping-common-survey-shapes) for supported routing.
- For every analytic figure, are survey version, cohort, eligible and inactive counts, eligible no-answer count, valid n, and multi-select denominator clear? State that eligibility is current-rule inference rather than historical display tracking.
- Are static checker results described only as evidence for the individual checks they cover? They do not judge wording quality, prove visual quality, or establish full WCAG conformance.
- For a conformance evaluation, are the product scope, essential task paths, representative views/states/branches, target criteria, findings, and unresolved gaps documented?
- Were representative public routes audited at desktop and 320 CSS px, then protected host and respondent routes audited with a disposable local fixture? Were all violations and results needing manual review addressed?

## Automated browser audit

Run `npm run a11y:audit -- [baseUrl] [route ...] [--authenticated] [--report path]` with Chrome available (set `CHROME_PATH` when Chrome is not at the macOS default path). Without routes, it scans `/`, `/admin/login`, `/signup`, `/forgot-password`, and `/reset-password` at 1280, 320, 360, and 390 CSS px, then checks that `prefers-reduced-motion` disables animations. The mobile samples cover WCAG reflow and KQA's common phone widths. The scan uses axe-core WCAG 2.0, 2.1, and 2.2 A/AA rules and checks title, heading, and overflow. Authenticated mode requires `KQA_A11Y_EMAIL` and `KQA_A11Y_PASSWORD`; it is local-only by default and signs in through the visible UI. Set `KQA_A11Y_INTERVIEW_ID` and `KQA_A11Y_RESPONDENT_TOKEN` to include interview tabs and the respondent questionnaire plus its same-origin iframe. Use disposable synthetic data; the audit does not click, save, submit, observe user sessions, or capture screenshots. `--report path` writes a JSON record containing source commit, scope, viewport, axe findings, incomplete checks, and manual-review limits. It excludes credentials, answer content, and private route tokens. To audit only public pages on a deployed URL, pass its origin as `baseUrl` without `--authenticated`.

This is a repeatable sample, not a scan of authenticated host screens, respondent questionnaires, every interaction state, question wording, or assistive-technology behavior. Review axe's incomplete results manually, test keyboard and screen-reader paths, and report the exact sample and methods. A zero-violation result does not establish WCAG conformance.

For new or materially changed questions, especially where purpose, interpretation, routing, sensitivity, or respondent burden is uncertain, use the reusable [`QUESTION_BLUEPRINT.md`](QUESTION_BLUEPRINT.md). It records the data-user need, respondent universe, construct/reference period, exact item and response options, intended interpretation, route, likely response-process risks, and testing plan. A template or expert review helps make assumptions visible; it is not respondent pretesting.

When an instrument is offered in another language or cultural context, adapt for meaning rather than literal wording. Record the reviewers and unresolved terms, and pretest with intended-language respondents in the planned mode when feasible. Set the document language correctly, but do not claim full localization: KQA's respondent shell and built-in controls are currently English, even when the authored questionnaire uses another `lang`. Report that mixed-language state as a limitation and verify comprehension before fielding.

When AI contributes to questionnaire drafting, collection, coding, or analysis, keep human accountability clear and record the AI's task, validation/oversight, and whether evidence is synthetic or from human respondents. For public research reporting, include method and language disclosures appropriate to the study. These practices draw on the revised [AAPOR Code of Professional Ethics and Practices](https://aapor.org/standards-and-ethics/) and its [Responsible AI Integration in Survey Research report](https://aapor.org/wp-content/uploads/2026/05/Responsible-AI-Integration-In-Survey-Research.pdf); they are research guidance, not a claim that KQA itself is an AAPOR member or that a questionnaire is compliant.

## Research basis and limits

- [WCAG 2.2 Quick Reference](https://www.w3.org/WAI/WCAG22/quickref/) provides the normative accessibility criteria. KQA targets Level AA.
- [WCAG Evaluation Methodology (WCAG-EM) 2.0](https://www.w3.org/TR/wcag-em-2/) is a W3C Group Note published 23 July 2026 with informative, technology-agnostic process guidance: define scope, explore essential functionality, select representative samples, evaluate them, and report findings. It is not a normative success criterion or a claim of conformance.
- [W3C WAI: Evaluating Web Accessibility](https://www.w3.org/WAI/test-evaluate/) explains that no evaluation tool alone can determine whether a site meets accessibility standards.
- [axe-core](https://github.com/dequelabs/axe-core) is the open-source rules engine used by KQA's browser audit; violations and incomplete results cover only the checks its rules can evaluate.
- [WCAG 2.2 SC 2.5.8: Target Size (Minimum)](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) explains the 24 × 24 CSS-pixel minimum and its exceptions.
- [WAI-ARIA Authoring Practices Guide: Tabs](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/) provides implementation patterns for tab interactions; it is guidance, not a conformance standard.
- [WAI-ARIA Authoring Practices Guide: Radio Group](https://www.w3.org/WAI/ARIA/apg/patterns/radio/) describes the keyboard behavior expected of custom radio groups; native radio controls are preferable when they fit.
- [WAI Forms Tutorial: User Notifications](https://www.w3.org/WAI/tutorials/forms/notifications/) explains how to make form errors and status messages concise and understandable.
- [WCAG 2.2 SC 4.1.3: Status Messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html) requires status messages that do not take focus to be programmatically determinable by assistive technology. KQA's routing announcement reports counts and leaves focus where the respondent placed it.
- [WCAG 2.2: On Input](https://www.w3.org/WAI/WCAG22/Understanding/on-input) explains predictable behavior and advance notice for a change of context caused by changing an input; a content change is not necessarily a change of context.
- [GOV.UK Design System: Radios](https://design-system.service.gov.uk/components/radios/) recommends keeping conditional questions simple and documents a known assistive-technology notification issue in its own reveal component. This does not establish accessibility of a KQA implementation.
- [ICO: Data minimisation](https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/data-protection-principles/a-guide-to-the-data-protection-principles/data-minimisation/) and [storage limitation](https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/data-protection-principles/a-guide-to-the-data-protection-principles/storage-limitation/) explain purpose-based collection and retention considerations; apply requirements appropriate to the context and jurisdiction.
- The Australian Bureau of Statistics [Forms Design Standards](https://www.abs.gov.au/statistics/standards/abs-forms-design-standards/2023) cover question wording, respondent burden, visual design, usability, accessibility, and testing. They are useful Australian evidence but do not make every ABS example suitable for KQA's different audiences.
- The UK Office for National Statistics' [check answers guidance](https://service-manual.ons.gov.uk/design-system/patterns/check-answers) supports a respondent review before completing a form, with a way to return to correct answers. Treat this as a pattern to adapt to KQA's submission and routing behavior, not as proof of usability in KQA.
- The UK Government Analysis Function's [Questionnaire Design Guidance](https://analysisfunction.civilservice.gov.uk/policy-store/questionnaire-design-guidance/) uses a respondent-centred framework and separates cognitive question testing from end-to-end usability testing; adapt it to the population and context.
- W3C WAI's [Multi-page Forms tutorial](https://www.w3.org/WAI/tutorials/forms/multi-page/) recommends logical groups and clear progress for long forms. The ONS [Hub and Spoke pattern](https://service-manual.ons.gov.uk/design-system/patterns/hub-and-spoke) demonstrates section-by-section survey navigation. GOV.UK's [question pages](https://design-system.service.gov.uk/patterns/question-pages/) and [error message guidance](https://design-system.service.gov.uk/components/error-message/) support one focused task per page, a clear Back route, and errors shown after a respondent tries to continue. W3C's [form notifications](https://www.w3.org/WAI/tutorials/forms/notifications/) recommends an error summary that receives focus. These patterns inform KQA's optional guided section flow; they do not establish a universal best mode, so keep `presentation: "all"` as the default and validate journeys with representative respondents.
- The US Census Bureau's [Statistical Quality Standard A2](https://www.census.gov/about/policies/quality/standards/standarda2.html) and [Appendix A2](https://www.census.gov/about/policies/quality/standards/appendixa2.html) distinguish respondent pretesting from expert review and cover functional verification and documentation; apply these as methods references, not as KQA certification criteria.
- The Census Bureau's [2025 question-template working paper](https://www.census.gov/library/working-papers/2025/adrm/rsm2025-07.html) describes recording the research question, question universe, wording/options, and testing concerns to connect subject-matter, methods, programming, and testing work.
- The CDC/NCHS [Cognitive Interviewing guide](https://www.cdc.gov/nchs/ccqder/question-evaluation/cognitive-interviewing.html) describes probes for comprehension, retrieval, judgment, and response selection.
- The Australian OAIC's [APP 3 guidelines](https://www.oaic.gov.au/privacy/australian-privacy-principles/australian-privacy-principles-guidelines/chapter-3-app-3-collection-of-solicited-personal-information) describe collection limits and minimisation under Australian privacy law; determine whether and how they apply to the host. Its [Privacy by Design guidance](https://www.oaic.gov.au/privacy/privacy-guidance-for-organisations-and-government-agencies/privacy-impact-assessments/privacy-by-design) recommends mapping information flows and addressing privacy risks early in design.
- [GitHub Primer Product Design](https://primer.style/product/) is a first-party product design-system reference for principles, components, and tokens.
- [GOV.UK Design System](https://design-system.service.gov.uk/) shares research-informed service patterns. Localize UK-specific language and conventions for KQA's Australian English.
- [GOV.UK Service Manual: User research](https://www.gov.uk/service-manual/user-research) describes methods for observing representative users completing realistic tasks; research complements automated checks.
- [GOV.UK Service Manual: Plan user research](https://www.gov.uk/service-manual/user-research/plan-user-research-for-your-service) recommends planning research at the start of each development phase and updating the plan as evidence changes.
- [U.S. Web Design System: Design principles](https://designsystem.digital.gov/design-principles/) says to start from real user needs and regularly test product assumptions with real people.
- [Pew Research Center: Writing Survey Questions](https://www.pewresearch.org/writing-survey-questions/) discusses question wording, response-option design, order effects, and pretesting.
- [AAPOR: Best Practices for Survey Research](https://aapor.org/standards-and-ethics/best-practices/) provides professional survey research and reporting practices; apply it with context rather than treating a static checker as a methods review.
- The revised [AAPOR Code of Professional Ethics and Practices](https://aapor.org/standards-and-ethics/) (June 2026) and [Responsible AI Integration in Survey Research](https://aapor.org/wp-content/uploads/2026/05/Responsible-AI-Integration-In-Survey-Research.pdf) add current guidance on transparency, AI's role, human oversight, evaluation, and human-subject protections.
- Pew's [Questionnaire Design and Translation](https://www.pewresearch.org/questionnaire-design-and-translation/) describes iterative linguistic and local review aimed at equivalence of meaning across languages and cultures.
- [Anthropic's frontend-design skill](https://github.com/anthropics/skills/commit/41bbe19d1a1a7eaab5e7bb9050a417e5c6cffc8f) is optional, subjective inspiration for brief-grounded visual direction and critique. KQA reviewed revision `41bbe19d1a1a7eaab5e7bb9050a417e5c6cffc8f` on 16 November 2026 (SHA-256 `d91970639e9f5c37682ac7ab60094d35f1c7c1f38d731bd56396563aee10c1d3`). It is not a standard and does not override the user's direction, WCAG, or KQA product policy.

These sources inform the policy; this policy is not a claim that KQA has passed a full accessibility audit, questionnaire-methods review, or usability study. Content review, respondent item pretesting, and task-based usability sessions require judgment and research with relevant people. Automated checks, browser screenshots, task observation, keyboard walkthroughs, and assistive-technology review each provide different evidence and should be recorded separately.
