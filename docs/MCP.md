# KQA MCP server

This is how an agent operates a live interview: people, questionnaire files, answers, and the private-link email. It is not the Next.js development endpoint.

`/_next/mcp` exists only while `next dev` is running. It reports compiler errors and routes. It cannot see interviews, and it is not present in production. Do not point an agent at it.

Writing a questionnaire file is still [`AGENT_PLAYBOOK.md`](AGENT_PLAYBOOK.md), with the sourced design rules in [`DESIGN_SYSTEM.md`](DESIGN_SYSTEM.md). The public bundle at `/api/docs/bundle.md` is for that job. It is not a way to change live data.

## Connect

Stateless Streamable HTTP. One JSON-RPC request, one JSON response. KQA supports MCP `2025-06-18`; initialization returns a version the server supports if the client requests another version. JSON-RPC batch arrays are rejected because this MCP version removed batching. There is no session and no long-lived stream.

| | |
|---|---|
| URL | `https://<your-host>/api/mcp` |
| Method | `POST` |
| Header | `Authorization: Bearer <key or KQA_MCP_TOKEN>` |
| Accept | `application/json, text/event-stream` |
| Body | A single JSON-RPC 2.0 message |

Requests with an `Origin` header are accepted only when it matches `KQA_PUBLIC_URL` or an origin in `KQA_MCP_ALLOWED_ORIGINS`. Set the optional value to comma-separated serialized origins such as `https://client.example,https://admin.example:8443`; do not include paths, queries, or trailing slashes. Invalid or unlisted origins receive HTTP 403 before bearer validation. Requests without `Origin` remain supported for server-to-server clients. This check applies to POST, GET, DELETE, and OPTIONS. Allowed browser origins receive an exact-origin CORS response; preflight permits POST with `Accept`, `Authorization`, `Content-Type`, and `MCP-Protocol-Version` headers. Cookies are not used.

`DELETE` answers 405. This server does not open an SSE channel and does not keep a session. A call with no bearer answers 401 and points ChatGPT at the OAuth discovery documents.

ChatGPT connects to `https://<your-host>/api/mcp` with no pasted token. It discovers `/.well-known/oauth-protected-resource` and `/.well-known/oauth-authorization-server`, then the host signs in and chooses Allow. That creates a key under Settings named after the app. The key is bound to the signed-in workspace. Revoke or delete the key to disconnect it. Other agents can use a workspace key or `KQA_MCP_TOKEN`.

Two credentials are accepted. The `KQA_MCP_TOKEN` environment variable is a tenant-bound service principal with full tool access that always operates in the legacy **Axion** workspace; a request cannot select a different tenant. A host can also create named keys under Settings. Each key is permanently bound to the signed-in workspace and has a name, a note, an optional expiry, a set of permissions, and a value. New named keys default to interview setup and aggregate-analysis read access. The host can grant only the capabilities the agent needs, and changes apply on the next request. The value is shown once. The database stores a SHA-256 hash plus a short fingerprint. A key can be revoked, restored, or deleted. Revoked, expired, and deleted keys are rejected.

### Credential permissions

`tools/list` returns only tools available to that credential, and the server checks permission again for every `tools/call`. Hiding a tool from the list is not the authorization boundary. `initialize` and `ping` remain available to any authenticated credential.

| Capability | Tools |
|---|---|
| `interviews:read` | `get_design_guidance`, `audit_questionnaire_design`, `list_interviews`, `get_interview`, `get_survey_html`, `list_versions`, `check_questionnaire`, `preview_questionnaire_version_patch`, `preview_questionnaire_block_patch`, `preview_questionnaire_required_patch` |
| `analytics:read` | `get_analytics_guidance`, `analyze_answers` |
| `respondents:read` | `list_people`, `get_person`, `get_answers`, `get_status`, `list_events`, `export_interview`, `get_mail_status` |
| `respondents:manage` | `add_people`, `update_person`, `remove_person`, `reopen_person`, `regenerate_link` |
| `interviews:manage` | `create_interview`, `update_interview` |
| `questionnaires:manage` | `apply_questionnaire_version_patch`, `apply_questionnaire_block_patch`, `apply_questionnaire_required_patch`, `upload_survey_version` |
| `email:send` | `send_invite` |
| `email:check` | `check_invite_delivery` |
| `interviews:delete` | `delete_interview` |

The `respondents:read` permission includes direct identifiers, private links, individual answers, and full interview exports; grant it only to agents that need respondent-level review. `interviews:delete` permanently removes an interview and related records. Existing named keys created before permissions were introduced retain full access until an owner edits them. Settings labels those credentials **Full access (legacy)** so owners can review and narrow them. OAuth connections keep the standard `host` scope for protocol compatibility, then ask for KQA tool permissions on the consent screen. Consent defaults to `interviews:read` and `analytics:read`; the selected permissions are stored on the resulting key and persist when it refreshes. An owner can change or revoke that key in Settings. The Axion deployment token remains full access and is rotated through the deployment host.

Neither credential is the admin password, the session cookie, or a respondent link. Send it only in the Authorization header. A token in the query string is rejected. A missing bearer, the admin cookie, or a query-string token is HTTP 401 and does not touch the database. A wrong server token is compared before tenant data is loaded. Any other bearer gets one API-key hash lookup and, when found, an active-tenant check. A failed lookup is the same HTTP 401.

A valid server token can read and write Axion data. An active key can read and write only its bound workspace. Suspended or missing tenants cannot use the server token, API keys, or OAuth refresh tokens. Anyone who has an active credential can delete interviews in its workspace. Treat both like the session secret.

Locally the value lives in `.env` (gitignored). Production on Vercel needs the same name, plus `KQA_PUBLIC_URL`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `IMAP_HOST`, and `IMAP_PORT`. Set those in the Vercel project. Do not paste the values into a chat, a doc, or a commit.

Example client entry (no secret in the file; the client reads the env var):

```json
{
  "mcpServers": {
    "kqa": {
      "url": "https://<your-host>/api/mcp",
      "headers": { "Authorization": "Bearer ${KQA_MCP_TOKEN}" }
    }
  }
}
```

## What the tools do

Every tool uses the same bearer check and per-key capability check. Tool definitions include MCP read-only, destructive, idempotent, and external-world hints. Arguments are checked against the published schema before the tool runs: required fields, types, enums, array sizes, and unknown fields. A string sent where an integer is required is rejected, and `list_events` rejects a limit below 1. An omitted `version` or `limit` still means the current version or the default of 30. Failures are a short error, not a stack trace. The questionnaire HTML is never put in an email. There is no score.

| Tool | What it does |
|---|---|
| `get_analytics_guidance` | Return versioned interpretation principles, a review checklist, and primary sources for descriptive survey analysis |
| `get_design_guidance` | Return KQA's versioned design principles, structured design plan, surface-specific visual profile, review checklist, and external sources |
| `extract_design_profile` | Parse CSS custom properties, legacy token JSON, or a bounded Design Tokens Format Module 2025.10 subset into semantic proposals; unresolved `$extends`, resolver-file modes, and external references are reported |
| `audit_questionnaire_design` | Run static questionnaire diagnostics and return the design review checklist; it does not render or certify the page |
| `list_interviews` | Host's interviews, open or closed, with people counts |
| `get_interview` | One interview and its question list. No HTML |
| `get_survey_html` | The stored file for a version |
| `list_versions` | Upload history without HTML |
| `check_questionnaire` | Run the checker. Nothing is stored |
| `create_interview` | Create from HTML. A failed check stores nothing |
| `update_interview` | Rename, notes, open, or close |
| `delete_interview` | Atomically delete the interview, versions, people, answers, events, analytics runs, and invite history. `confirmName` must match |
| `upload_survey_version` | Legacy upload for compatible changes; answer-impact findings return a signed preview and require acknowledgement |
| `preview_questionnaire_version_patch` | Check a complete candidate HTML file against the current version and saved answers; returns a short-lived token and stores nothing |
| `apply_questionnaire_version_patch` | Publish a previewed complete HTML file with a signed preview token, version/hash checks, and compatibility acknowledgement |
| `preview_questionnaire_block_patch` | Preview up to 500 add/update/delete/move operations for marked ordinary questions; preserves unrelated HTML bytes and stores nothing |
| `apply_questionnaire_block_patch` | Publish the reviewed question block operations with a signed preview token and compatibility acknowledgement |
| `preview_questionnaire_required_patch` | Preview 1–500 required/optional changes by question ID; edits only manifest booleans and stores nothing |
| `apply_questionnaire_required_patch` | Publish the reviewed required/optional changes with a signed preview token and compatibility acknowledgement |
| `list_people` | People, optional email, status, progress, mail state, private link |
| `get_person` | One person |
| `add_people` | Add people to a multi-user interview. Email is optional |
| `update_person` | Name, optional email, private note. An empty email clears it |
| `remove_person` | Remove the person, their answers, and their invite history |
| `reopen_person` | Unlock a submitted person |
| `regenerate_link` | New private link. The old one stops working. Nothing is emailed automatically |
| `get_answers` | Answers for review, with the label a host would read. No score |
| `analyze_answers` | Current-version descriptive summaries with participant scope, denominators, missingness, repeatable aggregate pagination, optional side-by-side status groups, and optional answer segmentation for up to 20 outcomes from one scan; no raw text or score |
| `get_status` | Open or closed, and not started / in progress / submitted |
| `list_events` | Recent audit rows |
| `export_interview` | `json`, `csv-wide`, `csv-long`, `md`, or `xlsx` (base64) |
| `get_mail_status` | Stored invite result. Does not open the mailbox |
| `send_invite` | Email one person's private link. One message per call |
| `check_invite_delivery` | IMAP check of the message id KQA stored. `delivered`, `bounced`, or `unknown` |

`get_design_guidance` is a deterministic instruction package; KQA does not include or call an LLM. Its review checklist is scoped to the requested surface, while `surface: "all"` returns the full checklist. The structured plan distinguishes task-based usability sessions with representative users, cognitive pretesting of question wording, and WCAG evaluation. It asks agents to report user profiles, realistic tasks, success criteria, observed findings, and limitations, or to state that usability was not tested. These research steps require human or agent judgment and are not static checker findings. `audit_questionnaire_design` runs the same static checker used by uploads and returns a questionnaire-specific checklist for rendered review. Static diagnostics cannot observe task completion or verify question quality, contrast, layout, keyboard interaction, motion, or assistive-technology behavior.

`extract_design_profile` accepts a `source` string up to 32 KiB, `format: "css"` or `"json"`, and an optional `surface` (`host`, `questionnaire`, or `analytics`; defaults to `questionnaire`). Supply only CSS custom properties or a token JSON object you are authorized to share. JSON supports legacy token files and a bounded subset of the [Design Tokens Format Module 2025.10](https://www.w3.org/community/reports/design-tokens/CG-FINAL-format-20251028/). It handles nested groups, `$root` tokens, `$value`, inherited `$type`, selected color/dimension/font-family forms, curly aliases, inline JSON Pointer references, and top-level light/dark groups. `$extends` group inheritance, resolver-file mode permutations, and external references are reported or left unresolved; the tool does not fetch additional files. KQA parses the text locally as inert input: it does not fetch URLs, execute CSS, store the source, or apply changes. The result includes a source hash, declaration paths/lines and scopes, uniquely proposed semantic mappings, ambiguous and unmapped tokens, candidate text/background contrast calculations, and a CSS overlay containing only recognized simple values. Name-based mappings and contrast pairings are proposals; review actual rendered use and states. Unsupported/custom scopes remain visible in the profile and may be omitted from the copyable overlay. Integrate a reviewed questionnaire theme inside its own HTML; host tokens do not cross the sandboxed iframe. Run `preview_questionnaire_version_patch` and inspect diagnostics/compatibility before publishing any resulting HTML.

The host console records the MCP tool name, success state, and safe credential identity (credential type, label, and stable credential ID). It does not record bearer values, answers, questionnaire HTML, or respondent links. The MCP `list_events` tool omits credential identity.

`get_analytics_guidance` returns the versioned `kqa-analytics/14` package for an integrated agent. It describes how to scope and interpret the descriptive summaries, compare status cohorts from one scan, explain no-answer counts and multi-select denominators, choose and code accessible charts, protect respondent privacy, and state limits on inference. Number summaries use exact Hyndman-Fan type-7 quantiles through n=256; larger cohorts use bounded-memory DDSketch estimates. The `numeric.quantiles` metadata identifies the method, 2% relative-value accuracy setting, 512-bin-per-sign cap, whether bins collapsed, and whether a relative error guarantee applies. Relative-value accuracy is not rank error; after bin collapse no relative error bound applies. Minimum, maximum, and mean use all valid numeric answers, and the memory limit does not suppress results. Raw values and histogram bins are not returned. Dates and text are not aggregated. For paginated `analyze_answers` results, reuse the returned `analysisRunId` as `runId` with `interviewId` and `offset`/`limit`; each completed aggregate run is tenant-bound, aggregate-only, and available for up to one hour. Pages share the same `asOf` and output after the initial scan completes. That initial participant scan is live and is not a database snapshot. The package also explains answer-defined segmentation across single-choice, dropdown, checkbox, and scale answers; up to 20 selected outcome questions can share one status scope, participant scan, and `asOf`. Checkbox groups overlap, and singleton and zero-count answer groups are returned without minimum-size suppression. Each `QuestionSummary` includes machine-readable `disclosureRisk` signals for singleton cohort, answered, no-answer, note-only, unmapped, valid-answer denominator, distribution values, and numeric summaries; segment groups also include their segment and status singleton signals. These identify counts of one only, do not measure all identification risks, and do not guarantee anonymity. It recommends considering inference risks from small groups and combinations of attributes. It is guidance only: KQA does not generate or certify the downstream analysis.

`numeric.quantiles.mappingRangeExceeded` is true when any value falls outside DDSketch's mapped range; that flag also means no relative-value error bound applies. Quartile estimates are clamped to the exact observed minimum and maximum to keep reported values finite and within the cohort's range.

For agent-authored questionnaire changes, prefer `preview_questionnaire_required_patch` when changing only required/optional flags. Send `interviewId` and a `changes` list of `{ "questionId", "required" }` entries (1–500, each ID once). The server edits only those manifest boolean values and preserves every other HTML byte. Review the returned per-question before/after values, current version, hashes, diagnostics, compatibility findings, and signed `previewToken`. If it passes, call `apply_questionnaire_required_patch` with the same changes, `expectedVersion`, `baseHash`, `candidateHash`, and `previewToken`. The token expires after 10 minutes and binds the authenticated tenant, interview, current version, base and candidate hashes, file name, and compatibility findings. If compatibility findings are present, also pass the preview's `compatibilityHash` and `acknowledgeCompatibilityImpact: true`. Apply reconstructs the candidate from the stored current version, verifies the token, and reruns the checker and compatibility comparison; no full HTML round-trip is needed.

For add/update/delete/move operations on ordinary questions, use `preview_questionnaire_block_patch` when the stored HTML has the optional stable markers in `FORMAT.md`. Send 1–500 unique operations: an add has `op: "add"`, a complete `question` and one-root `html` fragment; without a position it appends to the end of its section list and manifest. An update has `op: "update"`, `questionId`, the complete replacement `question` and `html`; it keeps the existing ID and section. A delete has `op: "delete"` and `questionId`. A move has `op: "move"` and `questionId`; `section` changes its section, omission keeps the current section, and `null` moves it to the unsectioned list. Adds and moves may set either `beforeQuestionId` or `afterQuestionId` to place the question relative to an unchanged question in the same target section. A move without a position appends to the target section. The question block root must carry `data-kqa-question-id` and be a direct child of the matching `data-kqa-question-list`. Each target section must have exactly one marked list. Targets that are missing, in another section, or also changed by the same batch are rejected as ambiguous. Custom questions, scripts or inline event handlers in supplied fragments, unmarked or ambiguous blocks, and deleting a question referenced by inline script are rejected. Review `operationChanges`, before/after question lists, diagnostics, compatibility findings and the signed `previewToken`. The preview includes complete manifest definitions for added and removed questions in `questionChanges.addedQuestions` and `questionChanges.removedQuestions`, so you can review their help, options, notes and bounds without fetching the HTML separately. If it passes, call `apply_questionnaire_block_patch` with the same operations, `expectedVersion`, `baseHash`, `candidateHash`, and `previewToken`. The apply call reconstructs the candidate from stored HTML, verifies the tenant-bound 10-minute token, reruns static and compatibility checks, requires the same acknowledgement when compatibility findings exist, and publishes through the current-version guard. Use the complete-file preview/apply pair for arbitrary page changes, custom question behavior, or HTML without stable markers.

For arbitrary agent-authored questionnaire changes, call `preview_questionnaire_version_patch` with the complete candidate HTML. It returns the current version and base hash, a hash of the normalized candidate HTML, a hash of compatibility findings, static diagnostics, compatibility findings computed against the current survey and saved answers, and a signed `previewToken`. Its `changes` object includes concise `questionChanges` and `sectionChanges`: added/removed IDs, counts, updated field names with before/after values, and moved IDs with one-based positions. The existing before/after question and section summaries remain available. Preview is non-mutating. If it passes, call `apply_questionnaire_version_patch` with the same complete HTML, `expectedVersion`, `baseHash`, `candidateHash`, and `previewToken` from that preview. Apply verifies the token and reruns the checker and compatibility comparison on the server; it does not accept preview diagnostics or a client-supplied manifest. The server rejects a missing, expired, altered, or out-of-scope token; a stale version/base hash; changed candidate HTML or compatibility findings; failed static checks; missing acknowledgement; or a concurrent publish. A successful apply adds a new immutable version and preserves prior versions and answers.

`upload_survey_version` remains for compatible legacy uploads. It also runs the compatibility check and publishes through the same optimistic version guard. If the check finds answer-impact diagnostics (KQA700–KQA704), the call stores nothing and returns `currentVersion`, `baseHash`, `candidateHash`, `compatibilityHash`, a signed `previewToken`, diagnostics, and the checker report. Review that response, then retry the same HTML with the returned version and hashes, `previewToken`, and `acknowledgeCompatibilityImpact: true`. The token has the same 10-minute expiry and tenant/interview/candidate binding as the explicit preview token. The server verifies it and reruns the checks before publishing. Prefer the explicit preview/apply pair for agent-authored changes so the impact is visible before the publish call.

Compatibility findings are checked against the saved answers visible during each tool call. The preview returns a `compatibilityHash`; apply and acknowledged upload calls reject if the findings changed before the publish call. A response committed after the compatibility read in that same call is outside the calculated snapshot.

`analyze_answers` uses the current immutable survey version. By default it includes invited, in-progress, and submitted people; set `submittedOnly` to true or pass a `statuses` list to narrow the cohort. Set `compareStatuses: true` to return separate summaries for each selected status alongside the combined result. Those status groups are computed in one participant scan and share the response's `asOf` time. This is one live read, not a frozen database snapshot. If `submittedOnly` and `statuses` are both supplied, `submittedOnly: true` can only be combined with `statuses: ["submitted"]`. KQA does not enforce a minimum cohort-size threshold, so singleton counts and percentages may be returned; integrated agents should disclose small-n limits and follow the host's disclosure rules. Use `questionId` for one question or `offset` and `limit` to page through questions. When a response includes `analysisRunId`, pass it back as `runId` together with `interviewId` and the next `offset`/`limit`; do not resend analysis filters. Pages from that tenant-bound, aggregate-only run share the same `asOf` and completed output for up to one hour. The initial participant scan is live and is not isolated by a database snapshot, so writes during that scan can affect the run. Runs are bounded in size and concurrency; if a run cannot be created, the tool returns an error instead of implying that separate reads are consistent. There is no historical time-window or trend analysis. `scope.participantCount` counts everyone in the selected status groups, including invited people with no answers; each `statusCohorts[].participantCount` is the count for that status. The legacy `respondentCount` properties are compatibility aliases for these participant counts; do not describe people with no answers as respondents. Each question's `cohortCount` also covers everyone in its selected status group, while `noAnswerCount` is the number without a non-empty stored value. KQA does not track whether conditional or routed questions were displayed or applicable, so `noAnswerCount` is not an item-level missingness or eligibility measure and may include people who never saw the question. The legacy `eligibleCount` and `missingCount` properties remain aliases for compatibility. `answeredCount` counts non-empty stored values, including values that no longer fit the current version; `unmappedResponseCount` reports those values, and they are excluded from valid numeric summaries and distributions. Option distributions expose their valid-answer denominator. Scale questions report a distribution and observed central category or pair: `scaleMedian` is the lower central category retained for compatibility, while `scaleMedianRange` gives the exact observed middle category or the two central categories. Ordinal category codes are never averaged, and no scale mean is calculated. Number summaries respect current minimum and maximum bounds and return n, minimum, Q1, median, Q3, mean, and maximum. The `numeric.quantiles` metadata reports exact Hyndman-Fan type-7 quantiles through n=256, or approximate DDSketch quartiles afterward with a 2% relative-value accuracy setting and a 512-bin-per-sign cap. It states whether bins collapsed; if they did, no relative error bound applies. Minimum, maximum, and mean use all valid numeric answers. This memory limit changes precision metadata only and does not suppress any numeric result. Text answers, names, notes, and private links are not returned. Every question summary carries `disclosureRisk` singleton signals: `singletonCohort`, `singletonAnsweredCount`, `singletonNoAnswerCount`, `singletonNoteOnlyCount`, `singletonUnmappedResponseCount`, `singletonDistributionDenominator`, `singletonDistributionValues` (current-version values with count 1), and `singletonNumericSummary`. This metadata is also present on per-status and segmented outcome summaries. It detects only counts of one and is not an anonymity guarantee. CSV exports use `cohort_count` and `no_answer` headers and include a note that item display eligibility is not tracked. Ordinal scale median rows retain the lower central category in `median` and include exact `scale_median_lower` and `scale_median_upper` columns; they carry `disclosure_risk_question_summary` JSON on each row plus the existing segment-level singleton columns when a row is grouped.
Set `segmentBy` to a current-version single-choice, dropdown, checkbox, or scale question to compare outcomes across its closed answer groups. Use `questionIds` to select between 1 and 20 outcomes in one participant scan; leave `offset` at 0 and set `limit` at least as high as the selected count. `questionId` remains available for a single outcome. If both are omitted, the tool pages through other questions and excludes the segmentation question. Each group includes its participant count and every selected outcome summary; with `compareStatuses: true`, status-specific summaries for all selected outcomes also share that scan and `asOf`. `disclosureRisk.singletonSegment` flags groups with one person, and `disclosureRisk.singletonStatusGroups` lists one-person status groups when status summaries are returned. These fields detect singleton counts only; an empty signal does not establish that a group is anonymous or safe to share. Single-choice, dropdown, and scale groups are disjoint. Checkbox groups overlap because a person can select multiple options, so their counts and percentages must not be added. When present, blank or note-only dimension responses appear as `No stored answer`, and values that do not match the current version appear as `Unmapped answer`. Outcome percentages use each group's valid-answer denominator. All closed answer options are returned, including singleton and zero-count groups. No minimum threshold is applied, and segmented aggregate output is not an anonymity guarantee; follow host disclosure rules. Segmentation is descriptive only, does not infer routed-question eligibility, and is not a score or causal analysis.

`send_invite` refuses, and does not write a failed mail row, when the person has no email, the interview is closed, or `KQA_PUBLIC_URL` is unset. The link in the message is always `KQA_PUBLIC_URL` plus the token. Pass `resend: true` to send again to the same address and the same link. Changing the email or rotating the link clears the current "sent" state and does not send on its own.

`check_invite_delivery` takes a `personId` only. It connects to IMAP, searches for the stored message id, and disconnects. It will not search the mailbox for anything else. `unknown` is shown to the host as "Not confirmed yet."

Person status stays `invited` ("Not started") until they save an answer. A mail gateway prefetching the link does not count as an open.

## Deliberately absent

- Login and logout. The bearer token is the credential.
- Saving or submitting as the candidate.
- Reading the mailbox, listing messages, or searching for anything other than a message id this app stored.
- A score, an answer key, or a second email (no submission receipt, no mail to the host).
- The Next.js devtools at `/_next/mcp`.
